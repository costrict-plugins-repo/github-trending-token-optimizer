This is a different kind of number from the [Terminal-Bench floor](/reference/benchmarks/terminal-bench/)
and the [Controlled A/B](/reference/benchmarks/controlled-a-b/). It is not a benchmark. It is the
author's own savings ledger over the **last 30 days** of everyday work, with all six levers running.
It shows the shape of the saving when everything fires. It does not predict yours.

Every figure on this page is the same 30-day window (2026-08-15 to 2026-09-14, snapshot taken
2026-09-14) from the same local ledger, and your dashboard computes the identical report from your
own sessions.

Delta reads ran at a small net loss this month: five events where the diff was longer than the
file. It is reported as measured, not hidden.

**Lean-output nudge.** When context fills past 25%, a short cache-safe note (injected as
`additionalContext`, never rewriting the existing prefix) tells the model to reason deeply but keep
its visible output lean. Each nudge records the session's pre-nudge average output tokens, then
meters the actual post-nudge output against it: `max(0, pre-nudge average − post-nudge average) ×
post-nudge turns`. Never an estimate, never negative, and never booked until post-nudge turns exist.

**Behavioral savers.** Quality nudges and loop detection prevent waste instead of removing it. Both
log an event when they fire and are low-volume by design; their payoff is avoided degradation and
avoided retry loops, not a headline dollar figure.

number of turns until that session's next real compaction event, priced at the per-turn cache-read
rate, and stops at the compaction. Lean resumes and other estimated-magnitude events are excluded

## First-read skeleton promotion

Large **code** files on first read that are unlikely to be edited soon can be served as a skeleton,
with the full original archived and retrievable via `expand`, a ranged Read, or a direct Edit. A
cohort (language plus size band) is only promoted to active serving after proof from real history:
the edit-within-5-turns rate must stay under 15% across 20 or more reads in 5 or more distinct
sessions.

A live tripwire watches every active cohort. If a cohort's live edit-after-skeleton rate ever
crosses 15%, it auto-demotes to measure-only and logs a `cohort_demoted` event. Demotions are
sticky to prevent flapping; re-promotion is explicit (`measure.py cohorts promote <lang:band>`) or
happens on the next history backfill. The full original is always archived before any skeleton is
served, and if archiving fails the full file is served unchanged (fail-open).

As of this snapshot the tripwire has demoted all four code cohorts: live edit-after-skeleton rates
of 16.0% (Python 16-64KB), 16.7% (Python 64-256KB), 50.0% (TypeScript 16-64KB) and 40.0%
(TypeScript 64-256KB), each above the 15% gate. The history backfill still rates the same cohorts
promotion-ready on their all-time edit rate (0.6% to 1.5%), which is exactly the disagreement the
tripwire exists to catch: live behaviour wins. Markdown cohorts stay measure-only by policy, because
a headings-only outline drops load-bearing prose. The first-read **retarget** that shipped in v2
serves the file you opened in full and moves the compression budget to skeletons of the related
files around it; see [Read cache](/features/read-cache/). Both flags are visible and toggleable in
`measure.py v5 status`.

## What is excluded

The benchmark harness writes its own test-fixture events into the same local ledger. In this window
that was 766 events (7.2M tokens, $14.47) tagged `f3bench-session-0001` and `test-session-*`,
recorded between 2026-08-31 and 2026-09-06. They are excluded from every figure on this page.

## Reproduce it on your own data

```bash
# The savings ledger behind the tiers above (last 30 days)
python3 scripts/measure.py savings
python3 scripts/measure.py savings --json

# Live compression events from your history database
python3 scripts/measure.py compression-stats --days 30 --json

# Cohort status and tripwire state
python3 scripts/measure.py cohorts status --json

# Full dashboard (the same report, visualized)
python3 scripts/measure.py dashboard
```

Your number is your own. Savings scale with how much read-heavy, multi-file work you do. Someone
who mostly chats will see less. Someone who lives in large codebases with long sessions will see
more. Token Optimizer computes this same report from your own history, so you never have to take
this month's figure on trust.
